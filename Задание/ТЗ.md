# ТЗ: OTA-оркестратор прошивок

## 1. Цель проекта

Система управляет раскаткой обновлений прошивки на парк устройств методом canary-деплоя: обновление сначала получает небольшой процент устройств, и только при подтверждённой стабильности раскатка расширяется на следующую группу. Решение о продвижении или откате стадии принимается автоматически на основе метрик успешности установки, без участия человека в штатном режиме.

Два сервиса разделяют ответственность: main service отвечает за взаимодействие с устройствами и администратором, Rollout Controller — единственный источник решений по раскатке.

## 2. Архитектура и поток данных

1. Устройство периодически обращается в main service с запросом на checkin, передавая текущую версию прошивки.
2. Main service определяет, попадает ли устройство под активную стадию раскатки, и публикует событие о checkin в Kafka.
3. После установки обновления устройство репортит результат через main service, который публикует событие в Kafka без интерпретации результата.
4. Rollout Controller потребляет события результатов, обновляет счётчики в Redis и периодически оценивает состояние активных кампаний.
5. При достижении порога Rollout Controller публикует решение — продвинуть стадию, откатить кампанию или завершить её.
6. Main service потребляет решения и обновляет состояние кампании в PostgreSQL, которое является источником правды для API и дашборда.

Main service не принимает решений о раскатке самостоятельно — только выполняет то, что решил контроллер, либо форсирует rollback по прямой команде администратора.

## 4. Main service

### 4.1 Публичный API для устройств

**POST /v1/devices** — регистрация нового устройства: device_model, начальная версия прошивки.

**POST /v1/devices/{device_id}/checkin** — основная точка входа.
Принимает текущую версию устройства. Логика:
- если статус устройства decommissioned — вернуть отсутствие обновления вне зависимости от активной кампании, дальше не проверять;
- найти кампанию со статусом running для device_model устройства;
- прочитать из Redis id активной стадии и её target_percent;
- вычислить, попадает ли устройство под этот target_percent;
- если попадает и current_version отличается от версии кампании — вернуть update_available с binary_url, checksum и stage_id активной стадии, иначе вернуть отсутствие обновления.

stage_id в ответе обязателен: устройство должно вернуть его без изменений в последующем report. Пока устройство устанавливает обновление, кампания может успеть продвинуться на следующую стадию, и на момент report активной стадией уже будет другая — без сохранённого stage_id результат будет ошибочно приписан не той стадии.

Побочные эффекты: обновление last_seen и current_version в Redis (ключи из раздела 6; checkin — единственное место, где устройство сообщает актуальную версию) и асинхронная публикация checkin-события в Kafka. Ответ устройству не должен ждать подтверждения записи в Kafka.

**POST /v1/devices/{device_id}/report** — репорт результата установки: campaign_id, stage_id (тот, что был выдан на checkin), result, опционально error_message. Main service валидирует принадлежность устройства к указанной кампании и стадии, генерирует event_id, синхронно сохраняет запись в update_attempts с этим event_id и публикует событие в Kafka с тем же event_id — он используется контроллером для дедупликации при повторной доставке (5.2). Интерпретация результата и запись в счётчики — вне ответственности main service.

### 4.2 Административный API

- **POST /v1/firmware** — регистрация новой версии прошивки.
- **GET /v1/firmware** — список зарегистрированных версий прошивки с фильтром по device_model; используется для выбора firmware_version_id при создании кампании.
- **POST /v1/campaigns** — создание кампании со списком стадий, включая target_percent, min_sample_size и success_threshold для каждой.
- **GET /v1/campaigns** — список кампаний, для страницы со списком кампаний на фронтенде.
- **GET /v1/campaigns/{id}** — кампания целиком: статус, полный список стадий с их status и entered_at (история переходов между стадиями для фронтенда), плюс success/failure rate и sample_size активной стадии, подмешанные через gRPC GetCampaignStatus (5.1).
- **POST /v1/campaigns/{id}/start** — перевод в running, активация первой стадии.
- **POST /v1/campaigns/{id}/pause** — переводит кампанию в paused. Checkin ищет только кампании со статусом running, поэтому пауза полностью останавливает выдачу обновлений.
- **POST /v1/campaigns/{id}/resume** — возвращает кампанию из paused обратно в running.
- **POST /v1/campaigns/{id}/rollback** — принудительный откат, аварийный рубильник. Вызывает ForceRollback у Rollout Controller и не меняет статус в PostgreSQL напрямую: изменение состояния идёт тем же пайплайном решений, что и автоматический rollback (5.1).
- **GET /v1/devices** — список устройств с фильтрами по device_model и status; last_seen и current_version в ответе подмешиваются из Redis поверх Postgres, если устройство уже отмечалось хотя бы одним checkin, иначе отдаются значения из Postgres (последнее — версия на момент регистрации).
- **POST /v1/devices/{id}/decommission** — переводит устройство в decommissioned. Такое устройство получает отсутствие обновления на checkin вне зависимости от активной кампании (4.1).

### 4.3 Consumer решений

Main service подписан на топик rollout.decisions. При получении события advance_stage, rollback или complete обновляет статус кампании и стадий в PostgreSQL. Обработка должна быть идемпотентной: у каждого decision-события есть уникальный decision_id, и повторная доставка того же события не должна привести к повторному переходу стадии. Для этого применённые решения фиксируются в отдельной таблице с уникальным constraint на decision_id, и перед применением проверяется, не была ли запись уже сделана.

### 4.4 Конкурентность

Checkin-хендлер публикует событие в Kafka через буферизированный канал, который обслуживает отдельная горутина-писатель — так HTTP-ответ устройству не зависит от задержек продюсера. Отправка в канал неблокирующая: реализуется паттерном select с default-веткой, чтобы при переполненном буфере хендлер не подвис, а событие просто отбрасывалось с логом. Доступность checkin важнее полноты аналитики по этому топику. При graceful shutdown сервис даёт буферу ограниченное время на слив, после чего завершает работу принудительно.

Report-хендлер устроен иначе: публикация в firmware.update-results синхронная и должна завершиться успешно до ответа устройству. Потеря этого события останавливает набор выборки на активной стадии и может привести к зависанию всей кампании, поэтому fire-and-forget здесь недопустим. Если публикация не удалась, хендлер возвращает ошибку, и устройство повторяет report самостоятельно.

## 5. Rollout Controller

### 5.1 gRPC-интерфейс

Сервис определяет два метода:
- GetCampaignStatus принимает campaign_id и возвращает текущую активную стадию, success/failure rate и размер выборки — используется main service для дашборда.
- ForceRollback принимает campaign_id, немедленно останавливает автоматическую оценку кампании и публикует в rollout.decisions решение rollback с новым decision_id — вызывается, когда администратор инициирует откат через административный API main service. Статус кампании в PostgreSQL обновляется тем же consumer'ом решений, что и при автоматическом rollback (4.3): у изменения состояния остаётся единственный путь применения независимо от того, кто его инициировал.

Вся автоматическая логика продвижения и отката живёт исключительно в контроллере. Main service либо читает статус, либо просит выполнить конкретное действие, но не вычисляет решения сам.

### 5.2 Consumer результатов

Отдельная consumer-группа читает топик firmware.update-results. На каждое сообщение инкрементируется соответствующий счётчик в Redis — success или failure для пары campaign_id и stage_id.

Kafka гарантирует доставку at-least-once, поэтому голый INCR не идемпотентен: одно и то же сообщение, доставленное повторно после ребаланса или сбоя, задвоит счётчик. Перед инкрементом нужна дедупликация — например, ключ вида campaign:{id}:stage:{stage_id}:seen:{event_id} с TTL, устанавливаемый через SETNX: если ключ уже существует, инкремент пропускается.

### 5.3 Логика принятия решений

Отдельный периодический процесс, независимый от Kafka consumer, обходит кампании со статусом running:
- если sample_size активной стадии меньше min_sample_size — действий не требуется;
- если failure_rate превышает 1 minus success_threshold — публикуется решение rollback, кампания переходит в rolled_back;
- если success_rate не ниже success_threshold и sample_size достаточен — публикуется advance_stage; если стадия последняя в кампании, вместо advance публикуется complete.

На малых выборках возможны случайные колебания метрики, поэтому решение принимается только если условие выполняется стабильно на протяжении нескольких циклов оценки подряд, а не по единичному замеру.

Счётчик подряд идущих стабильных циклов хранится в памяти Rollout Controller отдельно по каждой активной стадии. При рестарте сервиса счётчик обнуляется и оценка стабильности начинается заново — для пет-проекта это допустимое упрощение; если понадобится переживать рестарты, счётчик можно вынести в Redis по аналогии с остальным состоянием кампании.

### 5.4 Публикуемые события

Топик rollout.decisions, ключ — campaign_id. Тело события: campaign_id, decision_type, previous_stage_id, next_stage_id при наличии, decision_id для идемпотентности на стороне main service, timestamp.

### 5.5 Конкурентность

Kafka consumer и периодический evaluator работают как независимые горутины с общим контекстом отмены. Ребаланс consumer group не должен приводить к потере необработанных сообщений сверх того, что покрывает дедупликация из 5.2. При остановке сервиса нужно дождаться завершения текущего цикла evaluator, чтобы не оставить кампанию в промежуточном состоянии между чтением метрик и публикацией решения.

## 6. Redis

| Ключ | Тип | TTL | Пишет | Читает | Назначение |
|---|---|---|---|---|---|
| device:{device_id}:last_seen | string | 24 часа | main service | main service | online-статус устройства |
| device:{device_id}:current_version | string | 24 часа | main service | main service | версия, о которой устройство сообщило на последнем checkin; GET /v1/devices подмешивает это поверх Postgres |
| campaign:{id}:current_stage | string | нет | Rollout Controller | main service | id активной стадии, читается на каждый checkin |
| campaign:{id}:current_target_percent | string | нет | Rollout Controller | main service | target_percent активной стадии, пишется вместе с current_stage при переходе, читается на каждый checkin |
| campaign:{id}:stage:{stage_id}:success | counter | нет | Rollout Controller | Rollout Controller | накопленный счётчик успешных установок |
| campaign:{id}:stage:{stage_id}:failure | counter | нет | Rollout Controller | Rollout Controller | накопленный счётчик неудачных установок |
| campaign:{id}:stage:{stage_id}:seen:{event_id} | flag | несколько часов | Rollout Controller | Rollout Controller | дедупликация at-least-once доставки |

Счётчики пишет только Rollout Controller — двух источников записи в один ключ быть не должно.

Для вычисления bucket устройства состояние в Redis не требуется: используется детерминированное хэширование от device_id и campaign_id, например через FNV или CRC32, результат приводится по модулю 100. Устройство попадает под раскатку, если полученное число меньше target_percent активной стадии. Привязка стабильна и не требует хранения принадлежности устройства к стадии.

## 7. Kafka

| Топик | Ключ | Партиции | Производитель | Потребитель | Схема сообщения |
|---|---|---|---|---|---|
| device.checkins | device_id | 3+ | main service | аналитика, опционально | device_id, device_model, current_version, campaign_id, timestamp |
| firmware.update-results | campaign_id | 3+ | main service | Rollout Controller | device_id, campaign_id, stage_id, result, event_id, timestamp |
| rollout.decisions | campaign_id | 3+ | Rollout Controller | main service | campaign_id, decision_type, previous_stage_id, next_stage_id, decision_id, timestamp |

Партиционирование firmware.update-results по campaign_id гарантирует, что все результаты одной кампании обрабатываются последовательно относительно друг друга внутри партиции, что упрощает рассуждение о порядке при подсчёте счётчиков.

## 8. PostgreSQL

Таблицы соответствуют доменной модели из раздела 3: devices, firmware_versions, rollout_campaigns, rollout_stages, update_attempts. Дополнительно нужна таблица applied_decisions с полями decision_id (уникальный constraint), campaign_id, applied_at — для идемпотентного применения решений контроллера.

Индексы:
- devices по (device_model, status) — для поиска устройств при построении дашборда;
- rollout_campaigns по (device_model, status) — для поиска активной кампании конкретной модели при checkin, с ограничением не более одной running-кампании на модель;
- rollout_stages по (campaign_id, order_index) — для последовательного обхода стадий;
- rollout_stages частичный индекс по campaign_id where status = 'active' — ускоряет самый частый запрос в системе, поиск активной стадии на каждый checkin;
- update_attempts по (campaign_id, stage_id) — для расчёта метрик, если потребуется пересчёт из PostgreSQL в дополнение к Redis-счётчикам;
- update_attempts уникальный constraint по event_id — защищает от повторной записи, если сама публикация в Kafka или запись в БД повторяется после сетевого сбоя.

## 9. Идемпотентность и граничные случаи

- Повторный checkin устройства с уже установленной версией должен корректно вернуть отсутствие обновления — сравнение идёт по current_version, а не по факту участия в раскатке.
- Устройство, ушедшее в offline после получения обновления и не отчитавшееся за разумное время, должно в какой-то момент учитываться как timeout, а не оставаться неучтённым бесконечно. Для первой версии проекта достаточно упростить до success/failure, добавив timeout как отдельную задачу развития.
- Создание второй running-кампании для модели, у которой уже есть активная, должно быть запрещено на уровне бизнес-логики или constraint в PostgreSQL. Та же проверка действует при resume: если за время паузы для device_model появилась другая running-кампания, resume должен быть запрещён.
- Применение decision-события до того, как предыдущее решение по той же кампании обработано, недопустимо — порядок обработки должен соответствовать порядку публикации, что обеспечивается партиционированием по campaign_id.
- event_id, сгенерированный main service на report, защищает от повторной обработки одного и того же Kafka-сообщения при ребалансе или сбое продюсера. Он не защищает от случая, когда устройство само повторяет HTTP-вызов report из-за таймаута: это создаст новую попытку с новым event_id. Для пет-проекта это приемлемое ограничение, полноценная идемпотентность по ключу, переданному устройством, вынесена в раздел 13.

## 10. Docker Compose

Сервисы: ota-orchestrator (main service), rollout-controller, postgres, redis, kafka в режиме KRaft без отдельного zookeeper, опционально kafka-ui для визуальной отладки топиков, frontend как отдельный контейнер со статической сборкой.

## 11. Frontend

Минимальный набор экранов:
- список кампаний со статусами;
- страница кампании: текущая стадия, success/failure rate, история переходов между стадиями, кнопки pause, resume и rollback;
- список устройств с фильтрами по device_model и status, действие decommission;
- форма создания кампании с указанием стадий.

## 12. План реализации

1. Схема PostgreSQL и CRUD в main service для firmware, devices, campaigns без Redis и Kafka.
2. Логика bucket и checkin API поверх Redis.
3. Поднятие Kafka, публикация checkin и update-result событий из main service.
4. Rollout Controller: consumer результатов и запись счётчиков в Redis с дедупликацией.
5. Периодический evaluator и публикация решений.
6. Consumer решений в main service, идемпотентное применение к PostgreSQL.
7. Docker Compose, сборка всех сервисов вместе.
8. Frontend поверх готового API.

## 13. Возможные расширения

mTLS между main service и Rollout Controller, раскатка с разбивкой по географии или группам устройств вместо единого процента, отдельный сервис уведомлений на события rollback, миграция на Kubernetes с автоматическим масштабированием под нагрузку от количества устройств, идемпотентность report по ключу, который генерирует и передаёт само устройство, — защитит от дублирования попытки при повторе запроса на стороне устройства, а не только от повторной доставки внутри Kafka.
