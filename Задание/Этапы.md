# Поэтапный план реализации: OTA-оркестратор прошивок

Документ дополняет основное ТЗ (`ТЗ.md`) и разбивает проект на этапы. Каждый этап — рабочий, проверяемый инкремент: после него что-то реально можно потрогать через API, прежде чем переходить дальше. Инфраструктура добавляется постепенно, а не вся сразу: сначала Postgres, потом Redis, потом Kafka, потом второй сервис.

Готовые SQL-миграции для сверки вынесены в самый конец документа, в раздел «Приложение: миграции» — так они не попадаются на глаза раньше времени. В каждом этапе есть только спецификация того, что нужно реализовать: таблицы, поля, ограничения. Идея в том, чтобы сначала написать миграцию самостоятельно по спецификации и только потом сверить её с приложением.

## Инструмент миграций и договорённости

Рекомендуется `golang-migrate` — простой инструмент, не завязанный на ORM, каждая миграция это пара файлов `NNNN_описание.up.sql` / `NNNN_описание.down.sql`. Альтернатива — `goose`, разница непринципиальна.

Договорённости на весь проект:
- одна миграция — одно атомарное изменение схемы, которое можно откатить;
- у каждой миграции обязательно есть down-версия, даже если в пет-проекте её ни разу не придётся применять на практике — это дисциплина, которая окупается в реальной работе;
- уже применённая и запушенная миграция не редактируется задним числом — любое исправление идёт новым номером;
- миграции лежат в одной директории `/migrations` в корне репозитория и применяются к общей базе, даже когда появится второй сервис — Rollout Controller не имеет собственной схемы, только читает то, что нужно, через Redis и gRPC;
- статусные поля (status) реализуются как отдельные Postgres ENUM-типы, а не TEXT — база сама отбраковывает недопустимые значения, без CHECK-constraint со списком строк;
- колонки, которые могли бы называться голым словом вроде model, version, checksum, называются с префиксом сущности — device_model, fw_version, fw_checksum. Это защищает от путаницы при джойнах между таблицами, где столбец с одинаковым голым именем может означать разное, и часто требуется линтерами вроде sqlfluff;
- PK по умолчанию генерируется `uuidv7()`, а не `gen_random_uuid()` — uuidv7 сортируется по времени создания, что дружелюбнее к индексам и порядку строк при отладке, чем полностью случайный uuidv4.

Структура репозитория, к которой стоит прийти к концу этапа 5:
```
/ota-orchestrator (main service)
/rollout-controller
/migrations
/frontend
docker-compose.yml
```

## Этап 1 — Каркас и основная схема

**Цель.** Поднять main service и Postgres, реализовать хранение сущностей без какой-либо бизнес-логики раскатки.

**Что реализуется:**
- структура проекта, конфиг, health-check эндпоинт;
- POST /v1/devices — регистрация: device_model и начальная версия прошивки;
- GET /v1/devices — список устройств;
- POST /v1/devices/{id}/decommission — перевод в decommissioned (на checkin такое устройство всегда получает «нет обновления», см. этап 2);
- POST /v1/firmware;
- GET /v1/firmware — список версий прошивок, для выбора firmware_version_id при создании кампании;
- POST /v1/campaigns — создание кампании со списком стадий одним запросом; `device_model` копируется из выбранной firmware_version (денормализация для поиска running-кампании по модели), клиент не передаёт его отдельно;
- GET /v1/campaigns — список кампаний без фильтров (для пет-проекта достаточно);
- GET /v1/campaigns/{id} — кампания целиком: статус, полный список стадий с status и entered_at (история переходов для фронтенда);
- POST /v1/campaigns/{id}/start — draft → running, активирует первую стадию (order_index = 0), проставляет entered_at у стадии и started_at у кампании;
- POST /v1/campaigns/{id}/pause — running → paused;
- POST /v1/campaigns/{id}/resume — paused → running. Тот же partial unique index, что запрещает две running-кампании на device_model, срабатывает и здесь: если за время паузы для модели появилась другая running-кампания, resume должен вернуть понятную ошибку конфликта, а не голый constraint violation.

Redis и Kafka на этом этапе не нужны вообще.

**Сущности для БД на этом этапе.**

| Таблица | Поле | Тип | Ограничения |
|---|---|---|---|
| devices | id | UUID | PK |
| devices | device_model | TEXT | NOT NULL |
| devices | current_version | TEXT | NOT NULL |
| devices | status | DEVICE_STATUS | NOT NULL, default 'active' |
| devices | last_seen | TIMESTAMPTZ | nullable |
| devices | created_at | TIMESTAMPTZ | NOT NULL, default now() |
| firmware_versions | id | UUID | PK |
| firmware_versions | device_model | TEXT | NOT NULL |
| firmware_versions | fw_version | TEXT | NOT NULL |
| firmware_versions | fw_checksum | TEXT | NOT NULL |
| firmware_versions | binary_url | TEXT | NOT NULL |
| firmware_versions | created_at | TIMESTAMPTZ | NOT NULL, default now() |
| rollout_campaigns | id | UUID | PK |
| rollout_campaigns | firmware_version_id | UUID | NOT NULL, FK → firmware_versions.id |
| rollout_campaigns | device_model | TEXT | NOT NULL |
| rollout_campaigns | status | ROLLOUT_CAMPAIGNS_STATUS | NOT NULL, default 'draft' |
| rollout_campaigns | created_at | TIMESTAMPTZ | NOT NULL, default now() |
| rollout_campaigns | started_at | TIMESTAMPTZ | nullable |
| rollout_campaigns | completed_at | TIMESTAMPTZ | nullable |
| rollout_stages | id | UUID | PK |
| rollout_stages | campaign_id | UUID | NOT NULL, FK → rollout_campaigns.id |
| rollout_stages | order_index | INT | NOT NULL |
| rollout_stages | target_percent | INT | NOT NULL, диапазон [1, 100] |
| rollout_stages | min_sample_size | INT | NOT NULL |
| rollout_stages | success_threshold | REAL | NOT NULL, диапазон (0.0, 1.0] |
| rollout_stages | status | ROLLOUT_STAGES_STATUS | NOT NULL, default 'pending' |
| rollout_stages | entered_at | TIMESTAMPTZ | nullable |

Статусные поля реализованы отдельными Postgres ENUM-типами, создаются до таблиц: DEVICE_STATUS (active, decommissioned), ROLLOUT_CAMPAIGNS_STATUS (draft, running, paused, completed, rolled_back), ROLLOUT_STAGES_STATUS (pending, active, passed, failed).

Составные и бизнес-ограничения, которые не выражаются на уровне одной колонки:
- firmware_versions: уникальная пара (device_model, fw_version) — одна и та же версия для модели не регистрируется дважды;
- rollout_stages: уникальная пара (campaign_id, order_index) — у кампании не может быть двух стадий с одним порядковым номером;
- rollout_campaigns: не более одной кампании со статусом running на одну device_model одновременно. Обычный UNIQUE на device_model этого не выразит, потому что ограничение должно действовать только при status = 'running', а не для всех строк сразу — подумайте, каким видом индекса это можно ограничить.

Попробуйте написать 0001 сами, затем сверьте с готовой миграцией в приложении в конце документа.

**Как проверить.** Зарегистрировать прошивку и убедиться, что она находится через GET /v1/firmware. Создать кампанию с тремя стадиями — в ответе device_model совпадает с моделью прошивки, started_at ещё пустой. Запустить кампанию: первая стадия → active с entered_at, у кампании проставлен started_at, кампания видна в GET /v1/campaigns. Попытаться запустить вторую кампанию для той же device_model — partial unique index даёт constraint violation; поймать и превратить в понятный HTTP-код. Поставить первую на паузу, запустить вторую для той же модели, вызвать resume у первой — ожидается конфликт (две running на модель нельзя). Pause/resume без конкурента переключают статус туда и обратно.

## Этап 2 — Checkin и report поверх Postgres

**Цель.** Реализовать основную бизнес-логику раскатки, пока не отвлекаясь на Redis и Kafka. Стадия читается прямо из Postgres джойном — медленнее, чем будет в итоге, зато на этом этапе легче отлаживать саму логику без лишних движущихся частей.

**Что реализуется:**

**POST /v1/devices/{id}/checkin** — принимает текущую версию устройства. Порядок проверок (как в ТЗ §4.1):
1. если устройство `decommissioned` — сразу вернуть отсутствие обновления, дальше не проверять;
2. найти кампанию со статусом `running` для `device_model` устройства;
3. прочитать активную стадию джойном (на следующих этапах — из Redis);
4. вычислить bucket детерминированным хэшированием (`device_id` + `campaign_id` → FNV/CRC32 → mod 100) и сравнить с `target_percent`;
5. если устройство попадает под percent **и** `current_version` **отличается** от `fw_version` прошивки кампании — вернуть `update_available` с `binary_url`, `fw_checksum` и `stage_id` активной стадии; иначе — отсутствие обновления.

`stage_id` в ответе обязателен: устройство вернёт его без изменений в report. Пока идёт установка, кампания может продвинуться, и без сохранённого `stage_id` результат припишут не той стадии. Повторный checkin устройства, уже сидящего на версии кампании, всегда даёт «нет обновления» — сравнение идёт по версии, а не по факту участия в раскатке.

**POST /v1/devices/{id}/report** — тело: `campaign_id`, `stage_id` (выданный на checkin), `result` (`success` / `failure`; `timeout` в enum есть, но авто-джобы offline→timeout в v1 нет — ТЗ §9), опционально `error_message` (можно только логировать, в `update_attempts` колонки нет). Валидирует принадлежность device/campaign/stage и пишет строку в `update_attempts`.

**POST /v1/campaigns/{id}/advance-stage** (временный) — вручную переводит текущую active-стадию в `passed` и активирует следующую по `order_index`, либо переводит кампанию в `completed` с `completed_at`, если стадия была последней. Нужен, пока нет автоматики: через него тестируется продвижение. На этапе 6 ту же доменную функцию (не HTTP-хендлер) вызывает consumer решений.

На этом этапе в `update_attempts` ещё нет `event_id` — колонка появится на этапе 4 вместе с Kafka.

**Сущности для БД на этом этапе.**

| Таблица | Поле | Тип | Ограничения |
|---|---|---|---|
| update_attempts | id | UUID | PK |
| update_attempts | device_id | UUID | NOT NULL, FK → devices.id |
| update_attempts | campaign_id | UUID | NOT NULL, FK → rollout_campaigns.id |
| update_attempts | stage_id | UUID | NOT NULL, FK → rollout_stages.id |
| update_attempts | result | TEXT | NOT NULL, значения success/failure/timeout |
| update_attempts | reported_at | TIMESTAMPTZ | NOT NULL, default now() |

Кроме новой таблицы, нужен индекс на rollout_campaigns по (device_model, status): checkin на каждый запрос ищет running-кампанию по device_model.

Попробуйте написать 0002 сами, затем сверьте с готовой миграцией в приложении в конце документа.

**Как проверить.** Создать кампанию с двумя стадиями (25% и 100%), прогнать checkin для полусотни синтетических device_id на версии ниже целевой — примерно четверть получает `update_available` с `binary_url`, checksum и `stage_id`. Decommissioned-устройство и устройство уже на `fw_version` кампании — всегда «нет обновления». Вызвать advance-stage, прогнать checkin повторно теми же id — `update_available` получают все ещё не обновившиеся. На report с чужим campaign_id/stage_id — ошибка валидации, без записи в таблицу.

## Этап 3 — Redis как быстрый путь чтения

**Цель.** Убрать джойн из checkin на горячем пути, переложив чтение активной стадии на Redis. Postgres остаётся источником правды, Redis — проекцией для быстрого чтения.

**Что реализуется:**
- Redis в docker-compose;
- при старте кампании и на каждом advance-stage main service пишет в Redis, помимо изменения Postgres, пару ключей: id активной стадии и её `target_percent`;
- checkin **по-прежнему** сначала ищет running-кампанию в Postgres по `device_model` (pause/decommission/отсутствие кампании решаются здесь), а уже по найденному `campaign_id` читает `current_stage` и `current_target_percent` из Redis вместо джойна активной стадии. Только Redis без Postgres сломает pause: ключи стадии могут остаться после перевода в paused;
- `last_seen` и `current_version` устройства пишутся в Redis с TTL на checkin (checkin — единственное место, где устройство сообщает актуальную версию);
- GET /v1/devices подмешивает `last_seen` и `current_version` из Redis поверх строки из Postgres, если ключи не истекли; если устройство ни разу не отмечалось в Redis — значения из Postgres (`last_seen` пустой, `current_version` на момент регистрации);
- прогрев кэша при старте сервиса: main service проходит по всем running-кампаниям в Postgres и восстанавливает `current_stage` / `current_target_percent` в Redis. Без прогрева перезапуск или очистка Redis ломает checkin для уже идущих кампаний — это стоит специально воспроизвести.

Новых таблиц и миграций на этом этапе нет — меняется только то, откуда читается активная стадия.

**Redis-ключи:**

| Ключ | TTL | Пишет | Читает |
|---|---|---|---|
| `device:{device_id}:last_seen` | 24 часа | main service | main service |
| `device:{device_id}:current_version` | 24 часа | main service | main service |
| `campaign:{id}:current_stage` | нет | main service | main service |
| `campaign:{id}:current_target_percent` | нет | main service | main service |

**Как проверить.** Повторить сценарий из этапа 2 — поведение checkin не меняется, только реализация чтения стадии. Pause: running → paused, checkin перестаёт выдавать обновления, хотя ключи в Redis ещё могут лежать. `FLUSHALL` при running-кампании — checkin предсказуемо деградирует (нет ключей стадии), после рестарта main с прогревом снова работает, без паники. Merge: checkin с новой версией → GET /v1/devices сразу отражает её; после очистки Redis GET откатывается к версии регистрации, не к null.

На этапах 3–5 `current_stage` и `current_target_percent` пишет main service (контроллера ещё нет). По ТЗ §6 эти ключи пишет Rollout Controller — владельца и прогрев переносят на этапе 6.

## Этап 4 — Kafka: события checkin и report

**Цель.** Ввести асинхронный пайплайн событий и на практике увидеть разницу между fire-and-forget и надёжной доставкой на двух похожих на первый взгляд хендлерах.

**Что реализуется:**
- Kafka в режиме KRaft в docker-compose, топики `device.checkins` и `firmware.update-results` (партиции 3+), опционально kafka-ui;
- checkin-хендлер публикует событие асинхронно через буферизированный канал с неблокирующей отправкой (`select`/`default`) — при переполнении буфера событие дропается с логом, ответ устройству не зависит от Kafka;
- report-хендлер генерирует `event_id`, синхронно пишет строку в `update_attempts` с этим `event_id`, затем синхронно публикует в `firmware.update-results` с тем же `event_id`; если публикация не удалась — ошибка клиенту, устройство повторяет report. Fire-and-forget здесь недопустим: потеря события останавливает набор выборки на стадии.

**Топики на этом этапе (схемы как в ТЗ §7):**

| Топик | Ключ | Производитель | Поля сообщения |
|---|---|---|---|
| `device.checkins` | `device_id` | main service | `device_id`, `device_model`, `current_version`, `campaign_id`, `timestamp` |
| `firmware.update-results` | `campaign_id` | main service | `device_id`, `campaign_id`, `stage_id`, `result`, `event_id`, `timestamp` |

Ключ `campaign_id` у results гарантирует, что все результаты одной кампании идут в одну партицию и обрабатываются последовательно — это упрощает рассуждения о счётчиках на этапе 5.

**Изменение схемы на этом этапе.**

Таблица update_attempts уже существует и содержит данные с этапа 2. Нужно добавить колонку:

| Таблица | Поле | Тип | Ограничения |
|---|---|---|---|
| update_attempts | event_id | UUID | в итоге NOT NULL и UNIQUE |

Так как таблица не пустая, ограничения нельзя навесить одним шагом — нужно предусмотреть бэкафилл уже существующих строк значением до того, как включать NOT NULL и UNIQUE. Такой порядок в целом называется expand-contract: сначала расширяем схему, потом сужаем её ограничениями отдельным шагом.

Попробуйте написать 0003 сами, затем сверьте с готовой миграцией в приложении в конце документа.

**Как проверить.** Через kafka-ui или консольный consumer убедиться, что checkin и report публикуют сообщения с ожидаемыми ключами и полным набором полей. Остановить брокер — checkin остаётся успешным; report возвращает ошибку, а не тихую потерю события.

## Этап 5 — Rollout Controller: consumer и счётчики

**Цель.** Поднять второй сервис и научить его считать результаты, ничего пока не решая.

**Что реализуется:**
- новый сервис rollout-controller как отдельный Go-модуль и отдельный контейнер, без собственной схемы БД;
- gRPC-сервер с методами GetCampaignStatus и ForceRollback — на этом этапе ForceRollback можно оставить заглушкой с логированием, реальная логика будет добавлена на этапе 7;
- consumer-группа на топике `firmware.update-results`;
- на каждое сообщение — дедупликация через SETNX по ключу `campaign:{id}:stage:{stage_id}:seen:{event_id}` с TTL, и только если ключ не был выставлен ранее — инкремент счётчика `campaign:{id}:stage:{stage_id}:success` или `:failure`;
- main service: GET /v1/campaigns/{id} дополнительно вызывает gRPC GetCampaignStatus у контроллера и добавляет в ответ success/failure rate и sample_size поверх данных из Postgres. Если контроллер недоступен, эндпоинт возвращает данные из Postgres без метрик, а не падает целиком.

Новых Postgres-миграций на этом этапе нет — весь стейт контроллера живёт в Redis.

**Как проверить.** Опубликовать в топик вручную одно и то же сообщение с одинаковым event_id дважды — счётчик должен увеличиться один раз. Остановить и перезапустить контроллер посреди потока сообщений — после ребаланса consumer group счётчики не должны задвоиться на уже обработанных сообщениях. Отдельно — прогнать несколько report и убедиться, что GET /v1/campaigns/{id} отдаёт success/failure rate, соответствующий счётчикам в Redis; остановить контроллер и проверить, что эндпоинт всё равно отвечает, просто без метрик.

## Этап 6 — Автоматические решения

**Цель.** Заменить ручной advance-stage из этапа 2 автоматическим принятием решений на основе метрик.

**Что реализуется:**
- в контроллере — периодический evaluator, независимый от consumer'а, обходит running-кампании (логика ТЗ §5.3): sample_size < min_sample_size → ничего; failure_rate > 1 − success_threshold → rollback; success_rate ≥ success_threshold при достаточном sample → advance_stage, на последней стадии — complete. Решение только если условие стабильно несколько циклов подряд;
- счётчик подряд идущих стабильных циклов — в памяти контроллера, отдельно на активную стадию (при рестарте обнуляется — допустимое упрощение для пет-проекта);
- публикация решений в топик `rollout.decisions` (партиции 3+, ключ — `campaign_id`);
- в main service — consumer этого топика, идемпотентно применяющий решение к Postgres через `applied_decisions`;
- ручной advance-stage из этапа 2 либо удаляется, либо остаётся как debug; основной путь — decision-события.

**Топик `rollout.decisions`:**

| Поле | Описание |
|---|---|
| `campaign_id` | кампания |
| `decision_type` | `advance_stage` / `rollback` / `complete` |
| `previous_stage_id` | стадия, с которой уходим (если есть) |
| `next_stage_id` | следующая стадия при advance (если есть) |
| `decision_id` | уникальный id для идемпотентности на стороне main |
| `timestamp` | время решения |

Партиционирование по `campaign_id` обеспечивает порядок обработки решений одной кампании (ТЗ §9).

**Матрица применения decision в Postgres (consumer main service):**

| decision | Стадии | Кампания |
|---|---|---|
| `advance_stage` | текущая active → `passed`; следующая → `active` + `entered_at` | остаётся `running` |
| `complete` | последняя active → `passed` | → `completed`, проставить `completed_at` |
| `rollback` | текущая active → `failed` | → `rolled_back`, проставить `completed_at` |

**Владелец Redis-ключей стадии.** По ТЗ §6 `current_stage` / `current_target_percent` пишет Rollout Controller. Контроллеру для advance нужны пороги *следующей* стадии — они в Postgres, а контроллер ходит только в Redis/gRPC, поэтому статичный конфиг стадий публикуется в Redis.

Разделение ответственности после этого этапа:

1. **Main service** при create/start кампании пишет конфиг **всех** стадий: `stage:{stage_id}:target_percent`, `min_sample_size`, `success_threshold`.
2. **Инициализация активной стадии на start (и resume, если ключи протухли):** start — admin API main, не decision от controller. Чтобы checkin сразу видел новую кампанию, main **один раз** при start (и при resume, если `current_*` отсутствуют) выставляет `campaign:{id}:current_stage` и `current_target_percent` для первой/текущей active-стадии. Это единственное исключение: main пишет `current_*` только на вход в running, не на advance/rollback/complete.
3. **Controller** при `advance_stage` обновляет `current_stage` / `current_target_percent` по конфигу следующей стадии; при `rollback`/`complete` — удаляет или инвалидирует эти ключи (checkin и так не найдёт running в Postgres после применения decision, но чистые ключи проще отлаживать). Пишет до или после публикации в Kafka — потребители разные, порядок не критичен.
4. **Main** на advance/rollback/complete **больше не** пишет `current_*`: только применяет decision к Postgres.
5. **Прогрев:** main при старте по-прежнему восстанавливает `current_*` и `stage:*` для всех running-кампаний из Postgres (прогрев — восстановление проекции, не смена владельца decision-пути). Evaluator контроллера при обнаружении running без `current_*` может сам дописать их из `stage:*` — страховка на случай FLUSHALL без рестарта main.

| Ключ | TTL | Пишет | Читает |
|---|---|---|---|
| `stage:{stage_id}:target_percent` | нет | main service | Rollout Controller |
| `stage:{stage_id}:min_sample_size` | нет | main service | Rollout Controller |
| `stage:{stage_id}:success_threshold` | нет | main service | Rollout Controller |
| `campaign:{id}:current_stage` | нет | Controller (advance); main только на start/resume/прогрев | main service (checkin) |
| `campaign:{id}:current_target_percent` | нет | то же | main service (checkin) |

**Сущности для БД на этом этапе.**

| Таблица | Поле | Тип | Ограничения |
|---|---|---|---|
| applied_decisions | decision_id | UUID | PK |
| applied_decisions | campaign_id | UUID | NOT NULL, FK → rollout_campaigns.id |
| applied_decisions | applied_at | TIMESTAMPTZ | NOT NULL, default now() |

Таблица нужна для идемпотентности: unique на `decision_id` не даёт применить одно решение дважды.

Попробуйте написать 0004 сами, затем сверьте с готовой миграцией в приложении в конце документа.

**Как проверить.** Кампания с 2–3 стадиями от start до completed без ручных advance: устройства checkin/report, evaluator сам двигает стадии. Сразу после start (ещё до первого decision) checkin уже видит первую стадию — main инициализировал `current_*`. После advance checkin отражает новую стадию **до** обработки decision main'ом в Postgres — `current_*` обновил controller. Провал: заниженный success_threshold → `rolled_back`, стадия `failed`, `completed_at` проставлен. Одно decision дважды в топик — вторая попытка отсекается unique на `decision_id`.

## Этап 7 — Ручной откат через ForceRollback

**Цель.** Завести полноценный путь администраторского rollback через тот же пайплайн решений, что и автоматика.

**Что реализуется:**
- POST /v1/campaigns/{id}/rollback в main service вызывает gRPC ForceRollback у контроллера и **не** меняет статус в Postgres напрямую;
- ForceRollback: (1) помечает кампанию в in-memory set «не оценивать» (или эквивалент), чтобы текущий/следующий цикл evaluator её пропустил; (2) публикует decision `rollback` с новым `decision_id` в `rollout.decisions`;
- main обрабатывает его тем же consumer'ом и той же матрицей статусов, что и автоматический rollback (этап 6): единственный путь смены статуса кампании в Postgres;
- после применения decision кампания уже не `running` — evaluator и так её не берёт; in-memory флаг нужен, чтобы не опубликовать гонку «авто-advance vs ручной rollback» до прихода decision.

Миграций на этом этапе нет.

**Как проверить.** Запустить кампанию, на середине первой стадии вызвать rollback: статус → `rolled_back`, active-стадия → `failed`, evaluator в следующих циклах кампанию не трогает, повторный ForceRollback с тем же исходом идемпотентен на стороне Postgres (новый `decision_id` → no-op по уже `rolled_back`, либо явная проверка).

## Этап 8 — Индексация и устойчивость

**Цель.** Пройтись по системе с точки зрения производительности и отказоустойчивости, когда бизнес-логика уже стабильна и не отвлекает.

**Что реализуется:**
- graceful shutdown в обоих сервисах через errgroup и общий контекст отмены: HTTP-сервер, Kafka consumer/producer и периодический evaluator останавливаются согласованно, с ограниченным временем на слив буферов checkin-продюсера (этап 4);
- в rollout-controller при остановке **дождаться завершения текущего цикла evaluator** (ТЗ §5.5), чтобы не оставить кампанию между чтением метрик и публикацией decision; rebalance consumer group не должен терять сообщения сверх того, что покрывает дедупликация этапа 5;
- нагрузочная проверка checkin: десятки–сотни горутин бьют в эндпоинт — хэш и чтение Redis под конкуренцией;
- явные таймауты на запись в Kafka и Redis вместо дефолтов клиента.

**Индексы для БД на этом этапе.**

Новых таблиц нет, только индексы поверх уже существующих:
- devices — по (device_model, status): дашборд фильтрует устройства по модели и статусу;
- rollout_stages — по (campaign_id, order_index): последовательный обход стадий кампании;
- rollout_stages — частичный индекс по campaign_id where status = 'active': ускоряет поиск активной стадии без записей по завершённым;
- update_attempts — по (campaign_id, stage_id): расчёт метрик из Postgres, если понадобится сверка со счётчиками в Redis.

Индексы по (campaign_id, order_index) и partial по active — два разных индекса на одну таблицу, не один.

Попробуйте написать 0005 сами, затем сверьте с готовой миграцией в приложении в конце документа.

**Как проверить.** SIGTERM обоим сервисам во время нагрузки и посреди цикла evaluator — выход в заданный таймаут, без «оборванного» decision на полпути и без паники о недописанных буферах. EXPLAIN ANALYZE поиска active-стадии до/после 0005 — не seq scan.

## Этап 9 — Docker Compose и frontend

**Цель.** Собрать всё в единый стек и отдать фронтенд агенту.

**Что реализуется:**
- полный docker-compose.yml: ota-orchestrator, rollout-controller, postgres, redis, kafka (KRaft), опционально kafka-ui, frontend отдельным контейнером со статической сборкой;
- применение миграций отдельным шагом перед стартом ota-orchestrator, не при каждом запуске контейнера приложения;
- в API main service добавляются query-параметры фильтрации: `GET /v1/devices?device_model=&status=`, `GET /v1/firmware?device_model=`;
- frontend по ТЗ §11:
  - список кампаний со статусами;
  - страница кампании: текущая стадия, success/failure rate (из GetCampaignStatus), история переходов стадий (status + entered_at), кнопки **pause**, **resume** и **rollback**;
  - список устройств с фильтрами по `device_model` и `status`, действие **decommission**;
  - форма создания кампании с указанием стадий (target_percent, min_sample_size, success_threshold).

**Как проверить.** `docker-compose up` с нуля поднимает стек; через UI или API создаётся и проводится кампания от start до completed (и отдельно rollback) без ручных правок в контейнерах.

## Приложение: миграции

Готовые миграции для сверки. Имеет смысл открывать этот раздел только после того, как вы попробовали написать свою версию по спецификации в соответствующем этапе выше — иначе смысл упражнения теряется.

### Миграция 0001 — начальная схема

```sql
-- 0001_init.up.sql
CREATE TYPE DEVICE_STATUS AS ENUM ('active', 'decommissioned');
CREATE TYPE ROLLOUT_CAMPAIGNS_STATUS AS ENUM (
    'draft', 'running', 'paused', 'completed', 'rolled_back'
);
CREATE TYPE ROLLOUT_STAGES_STATUS AS ENUM (
    'pending', 'active', 'passed', 'failed'
);

CREATE TABLE devices (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    device_model TEXT NOT NULL,
    current_version TEXT NOT NULL,
    status DEVICE_STATUS NOT NULL DEFAULT 'active',
    last_seen TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE firmware_versions (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    device_model TEXT NOT NULL,
    fw_version TEXT NOT NULL,
    fw_checksum TEXT NOT NULL,
    binary_url TEXT NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (device_model, fw_version)
);

CREATE TABLE rollout_campaigns (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    firmware_version_id UUID NOT NULL REFERENCES firmware_versions (id),
    device_model TEXT NOT NULL,
    status ROLLOUT_CAMPAIGNS_STATUS NOT NULL DEFAULT 'draft',
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    started_at TIMESTAMPTZ,
    completed_at TIMESTAMPTZ
);

-- не больше одной running-кампании на device_model
CREATE UNIQUE INDEX one_running_campaign_per_model
ON rollout_campaigns (device_model)
WHERE status = 'running';

CREATE TABLE rollout_stages (
    id UUID PRIMARY KEY DEFAULT uuidv7(),
    campaign_id UUID NOT NULL REFERENCES rollout_campaigns (id),
    order_index INT NOT NULL,
    target_percent INT NOT NULL CHECK (target_percent BETWEEN 1 AND 100),
    min_sample_size INT NOT NULL,
    success_threshold REAL NOT NULL CHECK (success_threshold > 0 AND success_threshold <= 1),
    status ROLLOUT_STAGES_STATUS NOT NULL DEFAULT 'pending',
    entered_at TIMESTAMPTZ,
    UNIQUE (campaign_id, order_index)
);
```

```sql
-- 0001_init.down.sql
DROP TABLE rollout_stages;
DROP INDEX one_running_campaign_per_model;
DROP TABLE rollout_campaigns;
DROP TABLE firmware_versions;
DROP TABLE devices;
DROP TYPE ROLLOUT_STAGES_STATUS;
DROP TYPE ROLLOUT_CAMPAIGNS_STATUS;
DROP TYPE DEVICE_STATUS;
```

Типы дропаются последними и в обратном порядке создания — Postgres не даст удалить тип, пока на него ссылается колонка хотя бы одной ещё существующей таблицы.

```

```

### Миграция 0003 — event_id в update_attempts

Таблица уже может содержать данные, поэтому колонку нельзя сразу сделать NOT NULL UNIQUE. Паттерн expand-contract: сначала расширить схему, бэкафиллить, затем навесить ограничения.

```sql
-- 0003_update_attempts_event_id.up.sql
ALTER TABLE update_attempts ADD COLUMN event_id UUID;

UPDATE update_attempts SET event_id = uuidv7() WHERE event_id IS NULL;

ALTER TABLE update_attempts ALTER COLUMN event_id SET NOT NULL;
ALTER TABLE update_attempts ADD CONSTRAINT uq_update_attempts_event_id UNIQUE (event_id);
```

```sql
-- 0003_update_attempts_event_id.down.sql
ALTER TABLE update_attempts DROP CONSTRAINT uq_update_attempts_event_id;
ALTER TABLE update_attempts DROP COLUMN event_id;
```

На таблице такого размера, как в пет-проекте, все три шага спокойно уживаются в одной миграции. На проде с таблицей на миллионы строк `SET NOT NULL` и добавление constraint блокируют таблицу и обычно разносятся по отдельным миграциям, накатываемым в разное время — здесь достаточно знать, что так делают, специально усложнять пет-проект не нужно.
